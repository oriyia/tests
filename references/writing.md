Когда читать: пишешь новый тест — нужен пример хорошего и плохого теста, каким должен быть тест, куда положить тест и его данные.

# Как писать тест

## Пример

Пример. Требование: «экспорт отказывает, если период пуст».

Плохо — имя ничего не говорит, а проверка зелёная и на текущем коде, который отдаёт пустой файл:
требования тест не ловит.

```python
def test_export(self):
    result = export(Period.empty())
    self.assertIsNotNone(result)
```

Хорошо — до правки (класс ошибки уже заведён) падает с «EmptyPeriodError not raised», то есть
ровно по требованию:

```python
def test_export_rejects_empty_period(self):
    with self.assertRaises(EmptyPeriodError):
        export(Period.empty())
```

## Каким должен быть тест

- **Проверяет поведение через публичный вход**, а не внутренние вызовы: «вернул 120», а не
  «дважды вызвал `_sum`».
- **Одна причина упасть.** Сообщение о падении само говорит, что сломалось.
- **Ожидание — из требования, не из кода.** Ожидаемое значение, посчитанное тем же кодом, который
  проверяешь, — тавтология: тест зелёный при любой ошибке.
- **Детерминирован.** Время, случайность, часовой пояс, локаль задаёт тест. Плохо: код берёт
  текущую дату, тест сверяет месяц в заголовке отчёта с месяцем, когда его писали, — и через
  месяц краснеет. Хорошо: дата или часы приходят параметром, тест передаёт `2026-10-07`.
- **Изолирован.** Файлы — во временной папке, переменные окружения возвращаются как были, общих
  изменяемых данных между тестами нет; результат не зависит от порядка и параллельного запуска.
- **Без внешнего мира.** Сеть, чужие сервисы, часы подменяются на границе, которую проект не
  контролирует. Свои модули не подменяются: тест, где заглушено всё, зелёный при сломанном коде.
  Тест, который падает без сети, от неё зависит: это ошибка теста, а не среды. Скачивание при
  сборке или первом запуске (веса моделей, пакеты) ловит сборка и запуск без сети, если проект их
  проверяет.
- **Быстрый.** Медленный тест перестают запускать, и он перестаёт что-либо держать. Модульные
  тесты идут перед каждым коммитом, им отведены секунды; долгие — в отдельный набор, если проект
  отделяет долгие проверки.

## Где держать тесты

Сначала — как уже заведено в проекте. Тестов нет вовсе — по обычаю языка:

| Стек | Где | Имя файла |
|---|---|---|
| python | `tests/` в корне, повторяет структуру пакета; приёмочные — `tests/acceptance/` | `test_*.py` |
| node | рядом с кодом или в `tests/`, `__tests__/`; приёмочные Playwright — `tests/acceptance/` | `*.test.ts`, `*.spec.ts` |
| go | рядом с кодом, в том же каталоге; данные — `testdata/` | `*_test.go` |
| rust | модульные — `mod tests` в том же файле; через публичный API — `tests/` | `tests/*.rs` |

- **Тест, который команда не находит, зелёный навсегда.** Добавил файл — убедись, что команда его
  выполнила: тест есть в её выводе. Ловушки раннеров — в `profiles.md`.
- **Данные** — рядом с тестами (`tests/fixtures/`, `testdata/`), маленькие и читаемые; большие
  создаются в самом тесте.
- **Секретов в данных нет:** ключ или токен для теста создаётся в тесте, а не лежит файлом.
- **Новая библиотека для тестов** — в манифест и lock-файл в том же изменении; ставится заранее,
  не из команды тестов.
