Когда читать: тест или проверка красные после правки; хочется изменить тест, его ожидание или настройки проверок; перед отчётом — проверить свой дифф на ослабление.

# Красный тест после правки

Сначала выясни, кто прав — тест или код:

| Что выяснилось | Что делать |
|---|---|
| Код неверен | чинить код, тест не трогать |
| Изменилось требование (спецификация, план, слово человека) | менять ожидание теста; в отчёте и в сообщении коммита — что изменилось и откуда; если ожидание задаёт документ проекта — сначала новый документ |
| Тест проверял устройство, а не поведение: поведение то же, а он сломался | переписать проверку на поведение, не удалять |
| Ошибка в самом тесте | исправить и показать, в чём была ошибка |
| Тест то красный, то зелёный | найти причину: время, порядок, общее состояние, сеть, случайность; повторы и задержки — не исправление |

**Ослабление** — любая правка, после которой тест или проверка перестаёт ловить ошибку, ради
которой написан. Так не делать:

- удалить, закомментировать, пропустить тест (`skip`, `xfail`, `t.Skip`, `#[ignore]`), в том
  числе под предлогом недоступного окружения, которое тесту не нужно; оставить `.only`, который выключает остальные
  тесты файла;
- заменить точную проверку расплывчатой: `assertEqual(total, 120)` → `assertTrue(total)`,
  `toEqual(…)` → `toBeDefined()`;
- расширить допуск, перехватить исключение внутри теста, добавить повтор при падении;
- переписать ожидаемое значение на то, что выдал код, не поняв, почему оно другое; обновить
  снимок (snapshot, golden-файл), не прочитав разницу;
- подменить заглушкой то, что тест и проверяет;
- сузить, что запускает команда: исключить файл в настройках раннера, переименовать его так, что
  раннер его не видит;
- ослабить конфигурацию проверок проекта: очистить строку, заменить команду на более мягкую,
  дописать `|| true`, `--exit-zero`, убрать каталог из проверки;
- заглушить линтер или анализатор: `# noqa`, `# type: ignore`, `eslint-disable`, `//nolint`,
  исключение правила или файла в его настройках; снизить порог покрытия.

Перед отчётом проверь свой дифф:

```bash
p='skip|xfail|expectedFailure|\.only\(|t\.Skip|#\[ignore\]|noqa|type: ignore|eslint-disable|nolint|\|\| true|exit-zero'
git diff HEAD -U0 | grep -E "^\+.*($p)"                     # изменённые файлы
git ls-files -o --exclude-standard | xargs -r grep -HnE "$p"  # новые файлы
git diff HEAD --stat                    # удалённые строки в тестах — у каждой есть причина
git diff HEAD -- <настройки проверок>   # раннер, линтер, CI: не менялись или изменение согласовано
```

Не выходит сделать зелёным честно — остановись и скажи человеку: какой тест или проверка, как
падает (строка вывода), что пробовал, какая гипотеза. Красный тест с объяснением лучше зелёного,
который ничего не проверяет. Правило мешает — это запрос на изменение правила через человека, а
не обход.
